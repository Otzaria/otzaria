# ניסוי השוואת מסלולי WebView ב־Windows

תשתית לאיסוף נתונים עבור #4110. הכלי אינו משנה את ברירת המחדל של אוצריא,
אינו קובע ש־HWND עדיף, ואינו משלים לבדו את בדיקות התאימות של ה־issue.

## הרצה

נדרשים Windows, PowerShell 7 ו־build זהה של אוצריא במצב Release/Profile.
השתמש בפרופיל בדיקה: פתיחת האפליקציה והפעלת התוספים עשויות לשמור מצב כרגיל.
הכלי אינו מגבה, מוחק או משחזר נתוני משתמש, ואינו מסיים תהליכים בכוח.
סגור מופעים קודמים של האפליקציה לפני ההרצה.

```powershell
pwsh -File tool/perf_probe/run_webview_hosting_probe.ps1 `
  -Executable 'D:\Otzaria-test\otzaria.exe' `
  -OutDirectory 'D:\measurements\webview-idle-01' `
  -Scenario 'חמישה טאבי תוסף זהים, ארבעה מוסתרים, ללא הקלדה או גלילה' `
  -DisplaySetup '1920x1080, scaling 100%, viewport קבוע' `
  -Pairs 2 -Seconds 30
```

כל זוג כולל בקשת composition עם `FLUTTER_INAPPWEBVIEW_WINDOWS_FORCE_HWND=0`
ובקשת HWND עם ערך `1`. אין שינוי בברירת המחדל של build רגיל.
סדר ההפעלות מתחלף AB/BA. הדגל משתנה רק בסביבת תהליך הילד.
בכל הפעלה מכינים ידנית **אותו** עומס, מאשרים ב־`yes` את התאמת ההגדרות,
ולוחצים Enter להתחלת האיסוף. אישור אחר משאיר את הזוג לא מתאים להשוואה.
לאחר האיסוף סוגרים את האפליקציה כרגיל ומאשרים שהסתיימה.
תיקיית פלט קיימת אינה נדרסת. כשל משאיר את התוצאות החלקיות לבדיקה.

## נתונים ומגבלות

- `metadata.json`: SHA-256 של ה־EXE, תיאור התרחיש/תצוגה, מערכת, מעבדים
  לוגיים ופרטי GPU/דרייבר ככל שהם זמינים. לוג האפליקציה מוסיף גרסת אפליקציה,
  מצב בנייה, Flutter וה־WebView2 runtime הזמין שזוהה בבדיקת ההתקנה.
  יש לצרף בנפרד commit האפליקציה/הפורק, גרסאות התוספים ומצב חיסכון בחשמל.
- לכל ניסיון נשמרים גם `*-diagnostics.jsonl` ו־`*-backend.json`. הכלי נותן
  לתהליך הילד מזהה ריצה ונתיב אבחון נפרד, ומצליב run/PID/session וזמנים
  מול התהליך שהפעיל. יומן חסר, מקוטע, שייך לריצה אחרת או ללא כיסוי של
  חלון הדגימה משאיר את הנתונים לשימוש באבחון בלבד.
- רשומות `webview_backend` מתעדות יצירה, נוכחות בתחילת איסוף מאוחר וסיום
  הצמדה במארח האפליקציה, כולל מופע הרקע ב־Offstage. מזהה הצמדה אקראי
  נפרד מ־nativeViewId; החלפת controller או שימוש חוזר במזהה native אינם
  מקבלים את התצפית של המופע הישן. סיום הצמדה אינו אישור native disposal.
- `backend.observed` נקרא מה־getter הציבורי
  `WindowsInAppWebViewController.creationDetails`. `requested` נשאר
  נפרד. רק mode מוכר ומפורש הוא `verified`; תשובת native ישנה עם מספר
  בלבד, metadata חסר או mode לא מוכר נשארים unavailable. במערכות אחרות
  הנתון unsupported. סיבה חלקית/חסרה אינה מבטלת mode מאומת ואינה מוכיחה
  שלא היה fallback. HRESULT של יצירה נשמר unsigned32; שגיאות מניית
  תהליכים ממשיכות להישמר signed32 בחוזה שלהן.
- היקף התצפית הוא `nativeCreation`, ו־`ongoingModeVerified=false` תמיד.
  בפורק הנעול `c709de98`, מסלולי composition-controller ו־capture fallback
  מסתיימים לפני `createInAppWebView` מחזיר; reparent אינו בוחר backend חדש.
  ראו [מסלולי היצירה בפורק הנעול](https://github.com/Otzaria/flutter_inappwebview/blob/c709de98711cf34350c48df4c75e24d0879d5876/flutter_inappwebview_windows/windows/in_app_webview/in_app_webview_manager.cpp).
  זו אינה בדיקה רציפה של rendering, שלמות capture או נראות. אין polling
  או IPC נוסף לקריאת ה־getter. tick האבחון הקיים מספק חותמות כיסוי רק
  כאשר כלי זה הגדיר מזהה ריצה; הן אינן תצפיות backend חדשות.
  הצמדה מחדש של keepAlive יכולה לאמת mode בלי לשחזר את סיבת הבחירה המקורית.
- בכל `pair-NN.json`, `comparisonReady=true` דורש שני תהליכים טריים,
  שתי ריצות שלמות, אישור הגדרות, הרכב מארחים ו־viewport/DPR זהים, mode
  יצירה מאומת composition מול HWND, ואיסוף תקין לאורך הדגימה. viewport
  הוא חלון Flutter בזמן ההצמדה; אישור המשתמש נדרש גם לשינויים לאחר מכן.
  פתיחה/סגירה של מארח בזמן הדגימה, מצב מעורב, fallback ל־HWND בבקשת
  composition או אי־התאמה בבקשת HWND משאירים את הזוג noncomparable עם
  סיבה מפורשת. תצפיות והמדדים הגולמיים נשמרים גם אז. השדה אינו מעיד
  על התאמה מלאה של UI, כיסוי מנוע מלא או יתרון ביצועים.
  גרסה חסרה או שונה של האפליקציה/Flutter/OS/runtime, וכן build מסוג debug,
  מונעים אישור השוואה. ה־runtime הזמין אינו שאילתה חוזרת של renderer חי.
- קובץ JSONL לכל ניסיון: PID מדויק של המופע שהכלי פתח, תהליכי־הבן שנצפו,
  זמן CPU מצטבר, private commit ו־working set בבייטים. Working set אינו
  private commit וסכומו עשוי לספור דפים משותפים כמה פעמים.
- כל קשר הורות נבדק גם לפי `CreationDate`: תהליך שנוצר לפני ההורה הנוכחי
  אינו שייך אליו רק מפני ש־Windows השתמש שוב ב־PID. זהות שלא ניתן לאמת
  נספרת כחסרה ואינה מרחיבה את העץ; שורש חסר או מוחלף מפסיק את הניסיון.
  זמן היצירה נבדק גם לפני ואחרי קריאת המונים. ההשוואה ל־CIM מאפשרת רק
  הפרש קטן ממיקרו־שנייה, בהתאם לדיוק התאריך שלו, ולא חלון זמן שרירותי.
- CPU מחושב בין דגימות עם אותה קבוצת זהויות תהליך (PID + זמן יצירה).
  100% משמעו ליבה אחת מלאה, לא כלל המחשב. חילופי תהליכים, דגימה חסרה או
  counter שאינו תקין נותנים `null`, לא אפס. תהליכים שנולדו ונסגרו בין דגימות
  אינם נצפים: זהו אומדן מבוסס דגימות, לא מדידת CPU מלאה של כל ההרצה.
- ניסיון תקין מסתיים ברשומת `end` עם `complete=true`, רק לאחר בדיקת חיות
  נוספת בסוף האיסוף. סגירה בזמן ההמתנה האחרונה אינה נחשבת להשלמה.
  אין להשוות ניסיון חסר או להסיק שהשלמת הזמן מבטיחה שכל מוניו זמינים.
- `default` בשם קובץ הוא **בקשת composition** בלבד. אם RDP או כשל capture
  הובילו ל־HWND, נשמר mode זה בפועל והזוג אינו השוואת composition/HWND.
- הכלי לא אוסף זיכרון GPU, זמן אתחול, זמן חידוש או p95 של פריימים. יש
  לצרף אותם מכלי המערכת ומלוג הדיאגנוסטיקה של האפליקציה. אין לפרש חסר כאפס.

בצע ניסיונות נפרדים עבור idle, גלילה, resize, טאבים מוסתרים וחידוש.
פעולות ידניות אינן מתוזמנות אוטומטית; יש לתעד אותן ולחזור עליהן בעקביות.
השלם על שתי תצורות GPU לפחות ובדוק גם RTL, פוקוס, חפיפת תפריטי Flutter,
שינוי DPI וריבוי חלונות. רק אז ניתן להחליט על שינוי ברירת מחדל.

לבדיקת lifecycle, השווה את אותו רצף פתיחה, הסתרה, חידוש וסגירה חוזרת
באותו מסלול hosting ובאותה תצורת תוספים. בצע דגימת סרק לפני הרצף ואחריו
והצלב עם דיאגנוסטיקת האפליקציה למספר hosts ולהצלחת suspend/resume.
מספר תהליכי־בן אינו מספר hosts: כמה WebViews עשויים לשתף תהליך.

חוזי המקור: [זהות והורות ב־Win32_Process](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process#properties),
[דיוק תאריכי DMTF](https://learn.microsoft.com/en-us/dotnet/api/system.management.managementdatetimeconverter.todmtfdatetime).

## בדיקות הכלי

```powershell
pwsh -File tool/perf_probe/test_webview_hosting_probe.ps1
```

הבדיקות אינן פותחות את אוצריא: הן בודקות חישוב CPU, זהות תהליכים, חסרים,
מחזורים בעץ, שימוש חוזר ב־PID בזמן איסוף, שחרור handles, יציאה בהמתנה
האחרונה והפרדת משתני הסביבה. הן בודקות גם fallback, mixed modes, metadata
ישן, run/PID/session זר, החלפת מארח, זמנים מקומיים ו־UTC, יומן קטוע וכיסוי
חסר. ה־workflow מריץ אותן ב־Windows וב־Linux;
איסוף משאבים אמיתי עדיין דורש הרצה ייעודית ב־Windows.
